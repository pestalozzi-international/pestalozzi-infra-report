Payload CMS

What it is
Headless CMS built on Node.js. Self-hosted on Coolify alongside Supabase. Uses the same Postgres database — its own schema sits alongside the app's schema.
Database connection
Connects to Supabase Postgres via DATABASE_URI env var. Payload manages its own migrations — no conflict with app tables as long as schemas are separate.
Media storage
S3 storage adapter configured to point at Cloudflare R2. Editorial images uploaded in Payload land at r2/editorial/. URL returned immediately for use in content.
How the app reads it
REST or GraphQL API at cms.pestalozzi.org/api. App fetches content at build time (SSG) or runtime (SSR). Migrated page by page — hardcoded content first, then live fetch.

Cloudflare R2 — asset storage

Setup
Create bucket pestalozzi-assets in Cloudflare dashboard. Enable public access. Set custom domain assets.pestalozzi.org via CNAME. Takes ~20 minutes.
S3 compatibility
R2 implements the S3 API. Endpoint: https://<account-id>.r2.cloudflarestorage.com. Same SDKs, same tooling as AWS S3 — just a different endpoint and credentials.
Why not AWS S3
R2 has zero egress fees. S3 charges ~$0.09/GB egress. For a site serving videos globally, egress adds up fast. R2 free tier covers 10GB storage — plenty to start.
Connecting Payload
In Payload config, use @payloadcms/storage-s3. Set endpoint to R2 URL, region to auto, force-path-style to true. All media uploaded in Payload lands in R2 automatically.
Connecting self-hosted Supabase
In Supabase Storage env vars: STORAGE_BACKEND=s3, GLOBAL_S3_ENDPOINT=R2 URL, GLOBAL_S3_REGION=auto, GLOBAL_S3_FORCE_PATH_STYLE=true + R2 access keys.
Immediate fix needed
Download 5 missing videos + ~60 scraped images from Lovable CDN. Upload to R2. Update .asset.json files in production branch to point at R2 URLs. Site will be fully functional.

Supabase Postgres — shared database

Schema separation
public schema → app tables (alumni, donations, newsletter signups, etc). payload schema → Payload CMS tables (articles, team, events, media). Same Postgres instance, no conflict.
App connection
App uses Supabase JS client via VITE_SUPABASE_URL + VITE_SUPABASE_ANON_KEY env vars in Cloudflare Pages. Set these in Pages → Settings → Environment variables.
Payload connection
Payload connects via DATABASE_URI = postgresql://user:pass@localhost:5432/postgres?schema=payload. Payload runs its own migrations on first start.
Self-hosted vs cloud
Self-hosted on Coolify gives you full control, no Supabase Cloud egress costs, and lets you configure Supabase Storage to use R2 as the S3 backend — not possible on Supabase Cloud.

Supabase Auth

What it handles
User login/signup for any authenticated features on the site (alumni hub, donor portal, etc.). JWT tokens. Row-level security policies on Postgres tables.
Payload auth is separate
Payload CMS has its own auth system for admin users (editors logging into the CMS). This is independent of Supabase Auth — different user tables, different JWTs.

Coolify on Azure VM

What Coolify is
Open-source self-hosting platform. Manages Docker deployments, SSL certs, reverse proxy, env vars. Like a self-hosted Heroku/Railway on your own VM.
Services deployed on it

Start with a B2s (2 vCPU, 4GB RAM) — sufficient for Supabase + Payload at low traffic. Scale up if needed. Supabase docker compose recommends 4GB RAM minimum.

Build config

SSR via Nitro
@lovable.dev/vite-tanstack-config with nitro:true outputs a _worker.js bundle. Cloudflare runs this as a Worker — full SSR, not just static files. Server functions work.
Required env vars
VITE_SUPABASE_URL · VITE_SUPABASE_ANON_KEY · (future) VITE_PAYLOAD_URL. Set in Pages → Settings → Environment variables for both Production and Preview.
Branch strategy
Production branch: production. Preview branches: any other branch (including main) gets a preview URL. This lets you test Lovable changes before merging to production.

Cloudflare Worker — Canto sync (future)

What it does
Receives a webhook POST from Canto when an asset is approved. Authenticates the request. Downloads the asset binary from Canto's API. Writes it to R2 under /brand/. Logs metadata to Supabase.
Why a Worker
Workers run at Cloudflare's edge, have native R2 bindings (no S3 credentials needed in code), and are free up to 100k requests/day. Perfect for an infrequent asset sync trigger.
When to build this
Only when Canto supports webhooks and the media team is actively using Canto as the approval workflow. Not needed for the current manual phase.
Alternative: scheduled sync
Instead of webhooks, a Worker cron job runs every hour, queries Canto API for assets approved since last run, downloads and writes new ones to R2. Simpler if Canto doesn't support webhooks.
